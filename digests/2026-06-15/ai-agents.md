# OpenClaw 项目日报 - 2026-06-15

## 1. 今日速览

今日OpenClaw项目呈现极高的社区活跃度，过去24小时内产生了500条Issue和500条PR的更新，显示出强大的开发与用户反馈动能。尽管活动量巨大，但项目健康状况需审慎评估：Issue的关闭率（14.6%）和PR的合并率（15.8%）均处于低位，表明维护者的处理速度落后于社区提交速度。同时，大量P1级别的Bug（如消息重复、会话中断、内存泄漏）持续被报告，对核心体验构成了严峻挑战。今日发布了一个新的Beta版本v2026.6.8-beta.1，重点增强了Telegram和WhatsApp等渠道的交付稳定性。

## 2. 版本发布

项目于今日发布了新版本 **v2026.6.8-beta.1**。

*   **版本号**: `v2026.6.8-beta.1`
*   **更新内容摘要**:
    *   **Telegram 渠道增强**: 显著提升了消息发送的健壮性和丰富度。现在支持发送包含表格、列表、可折叠引用块的富文本消息。同时，优化了基于CLI的后端交付，改进了原生草稿迁移，并增强了富媒体边界的安全性。
    *   **WhatsApp 渠道增强**: 与Telegram类似，WhatsApp的消息交付也变得更加丰富和稳定。
    *   **破坏性变更与迁移注意**: 发布说明中未明确指出破坏性变更，但提到“退役了原生草稿迁移”。对于正在使用旧版草稿功能的用户，特别是通过API或自定义脚本进行管理的用户，建议在升级后检查草稿功能是否正常，并可能需要手动迁移或调整相关配置。

## 3. 项目进展

今日项目合并/关闭了多个重要PR，核心进展如下：

*   **Cron任务功能完善**:
    *   **PR #93149** (Open): 新增 `cron add --dry-run` 命令，允许用户在提交新定时任务前预览其预期行为。
    *   **PR #93110** (Open): 修复了Cron任务在独立环境中运行时，未能正确传递交付路由的问题，避免任务执行成功但结果未送达。
    *   **PR #92318** (Open, 自动合并武装): 强制要求Cron任务在声称“已通过消息工具发送”时，必须提供实质性的目标元数据作为凭证，以防止误报。
*   **渠道与交付稳定性修复**:
    *   **PR #93148** (Closed): **已合并**。解决了Telegram渠道消息发送后，未在SQLite数据库中记录的问题，确保消息历史可追溯。
    *   **PR #93135** (Closed): **已合并**。修复了Cron任务交付中，当工具不可用时未正确报告错误，而是生成误导性文本反馈给用户的问题。
*   **安全加固**:
    *   **PR #93152** (Open): 修复了 `loadProjectContextFiles()` 函数在遍历祖先目录时，可能越界到系统目录（如`/etc/`、`/root/`），加载不可信上下文文件的安全风险。
*   **会话管理改进**:
    *   **PR #71400** (Open): 提出了“自适应重置模式”，允许会话同时支持“每日重置”和“闲置超时”语义，避免单纯的“或”逻辑导致的误重置。

**结论**: 项目今日在“Cron任务”和“渠道消息交付”两个核心功能域取得了实质性的修复与增强。同时，一项关键的安全漏洞已被识别并提出了修复方案。

*   **#86508 [Bug]: Discord运行时发生EmbeddedAttemptSessionTakeoverError**：人气极高（👍: 4，评论: 9）。此问题与#85103、#86845等高度相关，表明会话文件锁定/冲突是导致多平台会话中断的常见根因，用户普遍感到困扰。

*   **#91016 [Issue]: 升级后DeepSeek Prompt Cache完全失效，烧钱**：获得了最高数量的👍（5个），反映了模型成本管理是用户核心关切之一。此问题直接关系到用户的经济利益，情绪反馈激烈。

**社区诉求分析**: 用户当前最渴望的是**稳定、可靠、可预测**的基础服务。他们能够接受新功能开发，但无法容忍回归性Bug（如消息重复）和核心流程的频繁失败（如会话中断）。对于API成本问题（如Prompt Cache失效）也高度敏感。

## 3. OpenClaw 在生态中的定位

- **技术定位**：通用 AI Agent 消息中枢框架。核心能力集中在多渠道交付（Telegram、WhatsApp、Discord）、Cron 定时任务、Memory 与 Codex 集成。比 Hermes Agent 更强调**自主智能体的后端编排**和**分布式部署**（Gateway 模型）。
- **优势**：渠道覆盖广、社区体量巨大（每日 Issue/PR 达 500+，是 Hermes 的 10 倍），功能生态丰富（Cron、Memory、安全加固）。但**维护效率严重滞后**，关闭率低导致积压指数级增长，用户信任受损。
- **差异点**：OpenClaw 更像一个**自托管 Agent 平台**，允许深度定制和管道插拔；Hermes Agent 则更像**面向最终用户的“一键部署”助手**，强调桌面端体验和即装即用。
- **社区规模**：OpenClaw 的 Issue/PR 数量级显著高于 Hermes，说明其用户基数更大、场景更多样，但也更容易暴露回归问题。Hermes 社区规模较小但粘性高，评论区互动深度高于 OpenClaw。
